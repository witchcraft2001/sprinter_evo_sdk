## Введение

**EvoSDK** — это набор инструментов и библиотек, который позволяет писать игры для
8-битных компьютеров на процессоре Z80 **на языке C**, а не на ассемблере. Вы пишете
обычный C-код, объявляете картинки и музыку в простом текстовом файле — а SDK берёт на
себя всё трудное: вывод графики, спрайты, музыку, чтение клавиатуры и джойстика.

Одна и та же программа собирается под две машины:

- **ZX Evolution / ATM Turbo** — расширенные клоны ZX Spectrum.
- **Sprinter** — другой мощный Spectrum-совместимый компьютер, работающий под
  операционной системой **DSS**.

Вы пишете игру **один раз**, а собрать её можете под любую из этих машин. Это руководство
показывает оба пути, с упором на сборку под **Sprinter**.

# Часть I. Основы

## Глава 1. Машины и SDK

Чтобы писать игры, вам не нужно глубоко знать «железо», но полезно представлять рамки, в
которых вы работаете.

**Экран.** Игровая картинка — это **320 пикселей в ширину и 200 в высоту**. Каждый пиксель
может быть одного из 16 цветов одновременно (об этом — в главе 2 и 7).

**Кадры.** Экран обновляется на экране **50 раз в секунду**. Одно такое обновление —
«кадр» (frame). Время в играх измеряется в кадрах: 50 кадров = 1 секунда. Плавная анимация
получается, когда вы меняете картинку каждый кадр.

**Память.** У вас немного памяти: код игры на C должен уместиться примерно в **55 КБ**.
Это достаточно для аккуратной игры, но требует дисциплины (см. главу 14). Картинки и музыка
в этот лимит **не входят** — они хранятся отдельно и при запуске игры целиком загружаются
в оперативную память. Дальше игра обращается к ним напрямую из памяти, ничего не дочитывая
с диска.

**Из чего состоит проект.** Папка вашей игры содержит:

- `main.c` — исходный код игры на C;
- `compile.bat` — список ресурсов (картинок, музыки, звуков);
- сами файлы ресурсов (`.bmp`, `.pt3`, `.afb`, `.wav`);
- `Makefile` — короткий файл, запускающий сборку.

Всё, что делает SDK, доступно через один заголовок — `evo.h`. Вы пишете в начале `main.c`:

```c
#include <evo.h>
#include "resources.h"
```

`evo.h` даёт функции SDK; `resources.h` — это файл, который **генерируется автоматически**
из вашего `compile.bat` и содержит имена ваших картинок и музыки (об этом — глава 4).

## Глава 2. Как устроена картинка

Прежде чем рисовать, нужно понять четыре понятия: **палитра**, **пиксель**, **тайл** и
**спрайт**. А ещё — **двойную буферизацию**.

### Палитра

Экран показывает 16 цветов одновременно. Но это не фиксированные цвета — это **16 ячеек**,
и в каждую вы можете положить любой цвет. Этот набор из 16 ячеек называется **палитрой**.

Каждый пиксель на экране хранит не сам цвет, а **номер ячейки палитры** (0..15). Когда вы
меняете цвет в ячейке палитры, мгновенно меняются все пиксели, нарисованные этой ячейкой.
Это мощный приём: например, плавно затемнив все 16 ячеек до чёрного, вы получаете эффект
«затемнения экрана» (fade), не перерисовывая ни одного пикселя.

Цвет в ячейке вы задаёте, указывая по одному значению на красный, зелёный и синий канал.
В коде это делается макросом `RGB222(r,g,b)`, где каждый канал — это число **0..3** (2
бита). Такой способ задания един для обеих машин: вы пишете цвет одинаково, а SDK сам
переводит его в формат конкретного «железа».

> **Откуда «по 2 бита».** На **Evo / ATM** это и есть родная глубина палитры — 2 бита на
> канал, всего 64 различимых цвета. У **Sprinter** аппаратная палитра богаче: **6 бит на
> канал** (значения 0..63, то есть RGB666 — десятки тысяч оттенков). Чтобы один и тот же
> код одинаково работал на обеих машинах, функции палитры (`pal_col`/`pal_custom`/…)
> принимают цвет в совместимом виде (2 бита на канал) и разворачивают его в 6-битный при
> выводе на Sprinter. При этом на Sprinter уже доступна **полная 256-цветная палитра**: она
> включается автоматически, если подложить 256-цветный ассет через `sprinter_*`-оверрайд
> (см. главу 5.5), а плавно гасить такую картинку помогает `pal_bright_fine` (глава 7).

### Пиксель и тайл

Рисовать каждый пиксель по отдельности — медленно. Поэтому графика собирается из
**тайлов** — квадратиков **8×8 пикселей**. Экран 320×200 — это сетка **40×25 тайлов**.

Большие картинки (фоны, заставки) — это просто наборы тайлов, которые SDK выводит за вас
одной командой. Вы работаете с координатами в «знакоместах»: тайл (0,0) — левый верхний
угол, тайл (39,24) — правый нижний.

### Спрайт

**Спрайт** — это маленькая движущаяся картинка **16×16 пикселей**, которую можно свободно
перемещать поверх фона: герой, враг, пуля, мячик. Спрайты — особенные:

- их может быть до **64** одновременно;
- у них есть **прозрачность**: часть пикселей спрайта не рисуется, и сквозь них виден фон
  (поэтому герой не выглядит как картинка в прямоугольной рамке);
- SDK сам **восстанавливает фон** там, где спрайт был в прошлом кадре, — вам не нужно
  вручную «стирать» старое положение.

### Двойная буферизация

Если рисовать прямо на видимом экране, игрок увидит процесс рисования — мерцание и
разрывы. Чтобы этого не было, есть **два экрана**: один показывается (видимый), на другом
вы рисуете (теневой). Когда кадр готов, вы вызываете `swap_screen()` — и теневой экран
становится видимым, а бывший видимый — новым теневым, чтобы рисовать следующий кадр.

`swap_screen()` ещё и **сам дожидается начала кадра**, поэтому картинка меняется плавно,
без рывков. Это сердце любой игры на этом SDK.

> **Важная тонкость.** Поскольку экранов два, статичная картинка (например, заставка)
> должна быть нарисована в **оба** экрана, иначе после `swap_screen()` вы увидите старое
> содержимое второго экрана. Приём прост: нарисовать → `swap_screen()` → нарисовать ещё
> раз. После этого картинка одинакова в обоих буферах.

## Глава 3. Ваш первый проект

Соберём минимальную программу — пустой чёрный экран, который не падает. Это проверит, что
тулчейн настроен.

### Структура

Создайте папку, например `mygame/`, и положите в неё три файла.

**`main.c`** — сама программа:

```c
#include <evo.h>
#include "resources.h"

void main(void)
{
    // пока ничего не делаем
}
```

Точка входа называется `main`, возвращает `void` и не принимает аргументов.

> **Важно: «выхода» из игры в привычном смысле нет.** Игра — это бесконечный цикл, который
> работает, пока включён компьютер. На **Evo / ATM** возвращаться из `main` некуда:
> операционной системы, в которую можно «выйти», там нет — если `main` завершится, машине
> просто нечего делать. Поэтому игровой цикл `while (1)` не заканчивается.
>
> На **Sprinter** игра запущена под операционной системой **DSS**, и в неё можно вернуться
> — для этого есть специальная функция `quit_to_dss()` (см. главу 12 и приложение A). Этот
> пустой пример ничего не делает и ни во что не выходит; как сделать корректный выход под
> Sprinter — показано дальше.

**`compile.bat`** — список ресурсов. Пока ресурсов нет, но файл нужен (из него берётся имя
выходного файла):

```bat
set output=mygame.scl
set title=" MY FIRST GAME"
```

`set output=` задаёт базовое имя; собранная игра получит имя `mygame.exe`. `set title=`
— это **полное сообщение о загрузке** (до ~31 символа), которое показывается на экране при
запуске игры. Поэтому пишите его целиком, например `" MY FIRST GAME IS LOADING"`: на
**Sprinter** загрузчик печатает эту строку как есть (отдельной строкой), на **Evo / ATM**
она выводится на экран загрузки. Указывайте `set title=` всегда — он нужен обоим таргетам.

**`Makefile`** — три строки, подключающие правила SDK:

```make
PROJECT := .
all: exe
include ../sprintersdk/sprinter.mk
```

(Путь `../sprintersdk/` — относительно папки вашего проекта; поправьте, если структура
другая.)

### Сборка и запуск

Из папки проекта:

```sh
cd mygame
make            # собрать
make clean      # очистить промежуточные файлы (папку _build/)
```

Если всё настроено, появится файл `mygame.exe` — это и есть игра в формате DSS, готовая к
запуску на Sprinter. (Как настроить компилятор — глава 16.)

Теперь у нас есть каркас. Наполним его.

# Часть II. Ресурсы

## Глава 4. Что такое ресурсы

**Ресурсы** — это данные игры, не являющиеся кодом: картинки, палитры, музыка, звуки,
сэмплы. Вы не «зашиваете» их в C-код; вместо этого вы **объявляете** их в `compile.bat`, а
обращаетесь к ним из кода по понятным именам.

### Как это работает

Каждая строка в `compile.bat` вида `set <тип>.<N>=<файл>` объявляет один ресурс:

```bat
set palette.0=back.bmp
set image.0=back.bmp
set sprite.0=balls.bmp
set music.0=level.pt3
set sample.0=bell.wav
set soundfx=effects.afb
```

- `<тип>` — что это: `palette`, `image`, `sprite`, `music`, `sample` или `soundfx`.
- `<N>` — число 0..255. Это **стабильный номер** ресурса; держите его уникальным в пределах
  типа. Порядок номеров можно делать с пропусками.
- `<файл>` — имя файла в папке проекта.

При сборке инструмент `resgen` читает `compile.bat` и создаёт файл **`resources.h`** с
удобными именами-константами. Имя строится из **имени файла** (без расширения, в верхнем
регистре) с префиксом по типу:

| Объявление | Что получите в `resources.h` |
|------------|------------------------------|
| `palette.0=back.bmp` | `#define PAL_BACK …` |
| `image.0=back.bmp` | `#define IMG_BACK …` |
| `sprite.0=balls.bmp` | `#define SPR_BALLS …` |
| `music.0=level.pt3` | `#define MUS_LEVEL …` |
| `sample.0=bell.wav` | `#define SMP_BELL …` |
| `soundfx=effects.afb` | `#define SFX_<имя>` на каждый эффект в банке |

Теперь в коде вы пишете осмысленно:

```c
draw_image(0, 0, IMG_BACK);   // нарисовать фон
music_play(MUS_LEVEL);        // включить музыку
```

Вам **не нужно** знать числовые значения — компилятор подставит их сам. Главное, чтобы имя
файла было валидным C-идентификатором (буквы, цифры, подчёркивание; не начинается с цифры).

> **Порядок назначения номеров.** Если вы используете `sprite`-листы (см. главу 5), важно
> понимать, что внутренние номера назначаются ресурсам по порядку. Меняя `<N>` или добавляя
> ресурсы, вы не ломаете имена `PAL_*`/`IMG_*` — обращайтесь по ним, а не по числам.

## Глава 5. Готовим графику

Графика — это **индексированные** картинки: каждый пиксель хранит номер цвета в палитре, а
не сам цвет — ровно та модель, о которой мы говорили в главе 2. Принимаются два формата
файлов:

- **BMP** — 16 цветов (4bpp) или 256 цветов (8bpp), несжатый, индексированный;
- **PNG** — индексированный (PLTE) **или** полноцветный/RGBA, без черезстрочности
  (non-interlaced). У PNG есть **нативная прозрачность** (альфа-канал / `tRNS`), и SDK её
  понимает напрямую (см. ниже и 5.3/5.4) — удобно, если редактор работает со слоями.

Большинство редакторов умеют и то, и другое: для BMP выбирайте «Indexed / 16 colors» или
«256 colors»; PNG можно сохранять индексированным или с прозрачным фоном.

> **Как PNG превращается в индексы.** Индексированный PNG берётся как есть (его палитра
> сохраняется в исходном порядке — важно для приёмов из главы 7). Полноцветный/RGBA PNG
> SDK сам сводит к палитре из его **различных непрозрачных** цветов — их должно быть **не
> более 256** (без потерь; если больше — сборка попросит уменьшить число цветов или
> сохранить индексированным). Полупрозрачность железо не умеет: пиксель либо непрозрачный,
> либо прозрачный — **любая прозрачность (alpha < 255) делает пиксель полностью прозрачным**.

### 5.1. Палитры

```bat
set palette.0=back.bmp
```

Палитра берётся **из палитры самого BMP-файла**. То есть вы рисуете картинку в нужных
цветах, и эти 16 (или 256) цветов и становятся палитрой `PAL_BACK`. Часто один и тот же
файл объявляют и как `palette`, и как `image` — тогда у картинки есть и пиксели, и её
палитра.

В коде палитру применяют функцией `pal_select(PAL_BACK)` — после этого экран показывает
цвета этой палитры (см. главу 7).

### 5.2. Изображения и тайлы

```bat
set image.0=back.bmp
```

Изображение — это картинка, которую SDK хранит как набор тайлов 8×8. Требования:

- **ширина и высота кратны 8** пикселям;
- 16 или 256 цветов.

Изображение можно вывести целиком (`draw_image`) или по одному тайлу (`draw_tile`) — это
удобно для «карт уровней», собранных из повторяющихся кусочков (стен, травы, кирпичей). О
рисовании — глава 8.

### 5.3. Спрайты

```bat
set sprite.0=balls.bmp
```

Спрайт-лист — это один BMP, на котором по сетке разложены **кадры спрайтов 16×16**.
Требования к листу спрайтов **строже**, чем к обычным изображениям:

- формат **256 цветов (8bpp)** — обязательно;
- ширина и высота кратны **16** пикселям.

Лист читается слева направо, сверху вниз: ячейка (0,0) — спрайт №0, следующая справа —
№1, и так далее. Имя `SPR_BALLS` указывает на **номер первого** спрайта листа; остальные
идут следом (`SPR_BALLS`, `SPR_BALLS+1`, `SPR_BALLS+2`, …).

**Прозрачность спрайтов** задаётся одним из двух способов:

- **PNG с прозрачностью** (рекомендуется): любой пиксель с альфой < 255 — прозрачный,
  сквозь него виден фон; полностью непрозрачные пиксели берут свой цвет из палитры. Ничего
  дополнительно указывать не нужно — рисуйте фигурку, а фон оставьте прозрачным.
- **BMP по индексу**: значимыми считаются **первые 16 цветов** (индексы 0..15) — видимые
  цвета спрайта; пиксель с индексом **16 или выше** считается прозрачным. Рисуйте спрайт
  цветами 0..15, а фон вокруг залейте любым индексом ≥16.

> Для BMP: если лист всего 16-цветный (4bpp), прозрачных пикселей в нём быть не может
> (индексов ≥16 нет) — спрайт будет непрозрачным прямоугольником; используйте 256-цветный
> лист **или** PNG с прозрачностью. Для **255 цветов спрайта + прозрачность** соберите
> проект с `PAL256=1` (глава 16): тогда у спрайтов цвета 0..254, а прозрачность — индекс 255.

### 5.4. Прозрачные тайлы (необязательно)

Иногда нужна прозрачность и у обычных тайлов фона (например, узор поверх стены). Рисуют
такой тайл функцией `draw_tile_key`, а прозрачность задают одним из способов:

```bat
set image.0=mask.bmp
set color_key.0=15        rem BMP: индекс 15 в image.0 будет прозрачным
```

Если же `image.0` — **PNG с прозрачностью**, его прозрачные пиксели становятся прозрачными
автоматически (объявлять `color_key` не нужно) — изображение помечается «keyed» само, и его
рисуют через `draw_tile_key`. В обоих случаях прозрачность — аппаратная.

### 5.5. Разная графика для Sprinter и Evo (необязательно)

Если игра собирается под обе машины, можно дать Sprinter **более богатую** версию картинки
(например, полноцветную 256-цветную), оставив Evo 16-цветную — не меняя ни `main.c`, ни
имена ресурсов. Для этого рядом с базовым объявлением добавьте Sprinter-оверрайд с префиксом
`sprinter_`:

```bat
set palette.0=hero.bmp           rem Evo: 16 цветов
set image.0=hero.bmp
set sprinter_palette.0=hero256.bmp   rem Sprinter: возьмёт эти файлы вместо базовых
set sprinter_image.0=hero256.bmp
```

Sprinter-сборка упакует файлы из `sprinter_*`, а **идентификатор и номер остаются от
базового** объявления (`IMG_HERO`, `PAL_HERO`) — значит `resources.h` и код одинаковы на
обеих машинах. Evo-сборка ключи `sprinter_*` просто не видит и берёт базовые файлы.

Правила: оверрайд-картинка должна совпадать с базовой по **размерам** (отличаются только
цвета); оверрайд-лист спрайтов — по **числу ячеек** (иначе номера спрайтов разъедутся, и
такой оверрайд будет проигнорирован с предупреждением). Для полноцветных спрайтов на
Sprinter собирайте с `PAL256=1` (см. главу 16).

## Глава 6. Готовим звук

Звук бывает трёх видов, и у каждого своя роль.

### 6.1. Музыка (PT3)

Фоновая музыка — это файлы формата **PT3** (модули трекера Vortex Tracker / Pro Tracker
3). Это привычный для Spectrum формат AY-музыки.

```bat
set music.0=level.pt3
```

Музыка играет в фоне и **не мешает** игре: SDK проигрывает её по прерыванию, кадр за
кадром, пока вы заняты своей логикой. Включается `music_play(MUS_LEVEL)`, выключается
`music_stop()`.

### 6.2. Звуковые эффекты (AFX)

Короткие эффекты (выстрел, прыжок, взрыв) хранятся **банком** в одном файле формата
**AFX** (`.afb` — банк эффектов AY-FX):

```bat
set soundfx=effects.afb
```

Из одного банка получается **много** констант `SFX_<имя>` — по одной на каждый эффект
внутри. Эффект проигрывается «поверх» музыки: `sfx_play(SFX_SHOOT, vol)`, где `vol` —
относительная громкость от -8 до 8.

### 6.3. Сэмплы (WAV)

Сэмпл — это «настоящий» оцифрованный звук (голос, рычание) — файл **WAV**:

```bat
set sample.0=meow.wav
```

Требования: **моно**, без сжатия (PCM). Сэмпл воспроизводится через простой ЦАП (Covox):
`sample_play(SMP_MEOW)`.

> ⚠️ Сэмпл — **блокирующий**: пока он играет, программа стоит и ждёт (прерывания
> запрещены). Используйте короткие сэмплы и в моменты, когда пауза незаметна.

# Часть III. Программирование игры

## Глава 7. Палитра и цвета

Палитра — это 16 ячеек цвета. Управляют ими так:

```c
void pal_select(u8 id);          // загрузить готовую палитру (PAL_*) целиком
void pal_copy(u8 id, u8* pal);   // скопировать готовую палитру в массив из 16 байт
void pal_col(u8 id, u8 col);     // задать ОДНУ ячейку id (0..15) цветом col (RGB222)
void pal_custom(u8* pal);        // задать все 16 ячеек из массива
void pal_clear(void);            // обнулить палитру (весь экран в чёрный)
void pal_bright(u8 bright);      // яркость экрана: 0=чёрный … 3=норма … 6=белый
```

Цвет задаётся макросом `RGB222(r,g,b)`, где каждый канал — 0..3:

```c
pal_col(0, RGB222(0,0,0));   // ячейка 0 — чёрный
pal_col(1, RGB222(3,0,0));   // ячейка 1 — ярко-красный
pal_col(2, RGB222(3,3,3));   // ячейка 2 — белый
```

Каждый канал — 0..3 (см. главу 2): это совместимый формат, одинаковый на Evo и Sprinter.
На Sprinter «железо» поддерживает больше оттенков (6 бит на канал), но SDK пока принимает
цвет именно в этом виде ради переносимости.

### Одна палитра на всё

Запомните: ячеек всего 16, и они общие для фона и спрайтов. Распространённый приём —
поделить их: например, цвета 0..5 отдать фону, 6..15 — спрайтам. Тогда вы берёте две
готовые палитры и собираете из них одну:

```c
static u8 palette[16];

pal_copy(PAL_BACK, palette);            // взять палитру фона
for (i = 0; i < 6; ++i) pal_col(i, palette[i]);   // её цвета 0..5 — в ячейки 0..5

pal_copy(PAL_BALLS, palette);           // взять палитру спрайтов
for (i = 6; i < 16; ++i) pal_col(i, palette[i]);  // её цвета 6..15 — в ячейки 6..15
```

### Эффект затемнения (fade)

`pal_bright` меняет яркость **всех** цветов сразу, не трогая пиксели. Это даёт плавные
переходы:

```c
// плавно погасить экран в чёрный
void fade_out(void) {
    u8 b;
    for (b = 3; b > 0; --b) { pal_bright(b - 1); delay(2); }
}
// плавно проявить
void fade_in(void) {
    u8 b;
    for (b = 0; b <= 3; ++b) { pal_bright(b); delay(2); }
}
```

Типичный сценарий смены экрана: погасить (`fade_out`) → нарисовать новую картинку (пока
экран чёрный, мусора не видно) → проявить (`fade_in`).

#### Плавный фейд для 256-цветных картинок (только Sprinter)

`pal_bright` даёт всего 4 ступени в диапазоне затемнения (уровни 3→2→1→0). На плоской
16-цветной графике это незаметно, но на 256-цветных фотографиях (см. главу 5.5) крупный
шаг яркости заметен и отдельные точки градиента гаснут раньше соседей.

Для таких картинок на Sprinter есть `pal_bright_fine(level)` — та же яркость, но
**32 линейных шага**: `level=32` — норма, `level=0` — чёрный. Публичный `pal_bright` и
макросы `BRIGHT_*` не меняются; на Evo функции нет, поэтому оборачивайте в `__SPRINTER__`:

```c
void fade_out(void) {
#ifdef __SPRINTER__
    u8 i;
    for (i = 1; i <= 16; ++i) { pal_bright_fine(32 - (i << 1)); delay(1); }  // 30..0
#else
    u8 b;
    for (b = 3; b > 0; --b) { pal_bright(b - 1); delay(2); }
#endif
}
```

Для 16-цветной палитры `pal_bright_fine` сам сводится к ближайшему грубому уровню — можно
звать единообразно. Подробности — в `plan.md` §9.1 и `HW_NOTES.md`.

## Глава 8. Рисуем фон: тайлы и изображения

```c
void select_image(u8 id);                 // выбрать изображение для draw_tile*
void draw_tile(u8 x, u8 y, u16 tile);     // нарисовать один тайл 8x8
void draw_tile_key(u8 x, u8 y, u16 tile); // то же, но с прозрачностью (по color_key)
void draw_image(u8 x, u8 y, u8 id);       // нарисовать изображение целиком
void clear_screen(u8 color);              // залить теневой экран цветом 0..15
void color_key(u8 col);                   // задать прозрачный цвет для draw_tile_key
```

**Координаты — в тайлах 8×8.** `draw_image(0,0,IMG_BACK)` ставит левый верхний угол
картинки в тайл (0,0). Экран — 40×25 тайлов.

**Целая картинка** рисуется одной командой:

```c
draw_image(0, 0, IMG_BACK);   // фон на весь экран
```

**Отдельные тайлы** — для карт из кусочков. Сначала выбираете изображение-источник, затем
рисуете из него тайлы по номеру:

```c
select_image(IMG_TILES);   // источник тайлов
draw_tile(5, 3, 12);       // тайл №12 из IMG_TILES в позицию (5,3)
```

В одном изображении-источнике может быть до 65536 тайлов; нумеруются они слева направо,
сверху вниз.

> Всё рисование идёт в **теневой** (невидимый) экран. Игрок увидит результат только после
> `swap_screen()` (глава 9).

## Глава 9. Игровой цикл, кадры и двойная буферизация

```c
void swap_screen(void);   // показать нарисованное; сам ждёт кадр; обновляет спрайты
void vsync(void);         // просто подождать начала следующего кадра
void delay(u16 frames);   // подождать N кадров (50 кадров = 1 секунда)
u32  time(void);          // сколько кадров прошло с запуска
```

Любая игра — это **бесконечный цикл**, и каждая его итерация рисует один кадр:

```c
while (1)
{
    // 1) обновить состояние игры (двигать героя, врагов, считать столкновения)
    // 2) нарисовать кадр в теневой экран (draw_image / draw_tile / спрайты)
    swap_screen();   // 3) показать кадр и дождаться следующего
}
```

`swap_screen()` делает сразу три вещи: дожидается начала кадра (ровно 1/50 секунды),
показывает теневой экран и обновляет спрайты. Поэтому отдельный `vsync()` перед ним не
нужен — он встроен. `vsync()` пригодится, только если вы хотите подождать кадр, ничего не
переключая.

`time()` удобно для таймеров: запомните `time()` в начале и сравнивайте, сколько прошло.
`delay(50)` — пауза в одну секунду.

## Глава 10. Спрайты

Спрайты — это до 64 движущихся картинок 16×16 поверх фона.

```c
void sprites_start(void);                    // включить систему спрайтов
void sprites_stop(void);                     // выключить
void set_sprite(u8 id, u16 x, u8 y, u16 spr); // поставить спрайт (x 16-бит: см. координаты)
```

### Как включить

Сначала нарисуйте фон и покажите его, потом включите спрайты:

```c
draw_image(0, 0, IMG_BACK);   // фон в теневой экран
swap_screen();                // показать фон
sprites_start();              // теперь спрайты будут выводиться поверх него
```

`sprites_start()` работает медленно (копирует фон для системы восстановления), поэтому
зовут его один раз при старте уровня, а не каждый кадр.

### Как ставить спрайты

`set_sprite(id, x, y, spr)`:

- `id` — номер спрайта в списке, **0..63**. Это «слот»; вызывая `set_sprite` с тем же
  `id`, вы перемещаете тот же спрайт.
- `x`, `y` — координаты (см. ниже про точность);
- `spr` — какую картинку показать (например `SPR_BALLS`, `SPR_BALLS+1`, …). Если передать
  `SPRITE_END`, вывод списка на этом спрайте прекращается.

После `sprites_start()` спрайты выводятся **автоматически при каждом `swap_screen()`** —
вам нужно лишь обновлять их позиции. Фон под ними восстанавливается сам, стирать вручную не
нужно.

### Координаты спрайтов — внимание!

Координата `y` — обычная, в пикселях (0..184). А вот **`x` задаётся с шагом 2 пикселя**:
значение `x` — это «полупиксели», диапазон **0..152**. То есть `x=10` — это 20-й пиксель
экрана. Так сделано ради совместимости с EvoSDK. Практический вывод: горизонтальный
диапазон движения — 0..152 (это покрывает все 320 пикселей: 160 шагов минус 8 на ширину
спрайта).

> **Нативный режим (Sprinter, `NATIVE=1`).** Если проект собран нативно (глава 16), `x` —
> это **обычный пиксель** (0..303 на экране 320), а `y` — до 240 (экран 320×256). Никаких
> «полупикселей»: спрайт можно поставить в любую точку и двигать по 1 пикселю. Этот режим —
> для новых проектов; портам EvoSDK оставляйте `NATIVE=0` (шаг 2px).

> **Клиппинга нет!** Спрайт нельзя частично «высунуть» за край экрана — координаты должны
> держать его целиком на экране (совместимость: `x` 0..152, `y` 0..184; натив: `x` 0..303,
> `y` 0..240). Иначе SDK его просто не нарисует.

### Пример: один спрайт под управлением

```c
set_sprite(0, x, y, SPR_HERO);   // поставить героя
swap_screen();                   // показать (и вывести спрайт)
```

## Глава 11. Звук

```c
void music_play(u8 mus);        // включить музыку (MUS_*)
void music_stop(void);          // выключить музыку
void sfx_play(u8 sfx, i8 vol);  // проиграть эффект (SFX_*), громкость -8..8
void sfx_stop(void);            // остановить все эффекты
void sample_play(u8 sample);    // проиграть сэмпл (SMP_*) — БЛОКИРУЮЩЕ
```

Музыка и эффекты играют сами по себе в фоне — вызвали и забыли:

```c
music_play(MUS_LEVEL);          // фоновая музыка уровня
...
sfx_play(SFX_SHOOT, 4);         // выстрел, средняя громкость
```

Музыка и эффекты не тормозят игру. Сэмплы (`sample_play`) — наоборот, **останавливают**
игру на время звучания, поэтому применяйте их осторожно (короткие звуки, незаметные паузы).

## Глава 12. Управление

```c
u8   joystick(void);            // джойстик + курсорные клавиши -> флаги JOY_*
void keyboard(u8* keys);        // состояние всех клавиш -> массив из 40 байт
u8   mouse_pos(u8* x, u8* y);   // позиция мыши
void mouse_set(u8 x, u8 y);     // задать позицию мыши
void mouse_clip(u8 xmin, u8 ymin, u8 xmax, u8 ymax); // ограничить зону мыши
u8   mouse_delta(i8* x, i8* y); // смещение мыши с прошлого опроса
```

### Джойстик

Самый простой ввод. `joystick()` возвращает биты — проверяйте их флагами:

```c
u8 j = joystick();
if (j & JOY_LEFT)  x -= 1;
if (j & JOY_RIGHT) x += 1;
if (j & JOY_UP)    y -= 1;
if (j & JOY_DOWN)  y += 1;
if (j & JOY_FIRE)  shoot();
```

Курсорные клавиши и пробел опрашиваются заодно с джойстиком, так что управление работает и
без физического джойстика.

### Клавиатура

`keyboard` заполняет массив из **40 байт** — по байту на клавишу. Клавиши адресуются
константами `KEY_*` (`KEY_A`, `KEY_SPACE`, `KEY_ENTER`, цифры и т. д.). В каждом байте два
флага:

- `KEY_DOWN` — клавиша **сейчас удерживается**;
- `KEY_PRESS` — клавиша **была нажата** с прошлого опроса (сбрасывается после `keyboard`,
  удобно ловить однократное нажатие).

```c
static u8 keys[40];
keyboard(keys);
if (keys[KEY_SPACE] & KEY_DOWN)  fire();          // пока держат пробел
if (keys[KEY_ENTER] & KEY_PRESS) toggle_pause();  // один раз на нажатие
```

### Мышь

`mouse_pos(&x, &y)` даёт координаты курсора (по `x` разрешение понижено вдвое, как у
спрайтов); возвращаемое значение — флаги кнопок `MOUSE_LBTN`/`MOUSE_RBTN`/`MOUSE_MBTN`.
`mouse_clip` ограничивает зону движения курсора (по умолчанию 0..160 по x, 0..200 по y).
`mouse_delta` даёт относительное смещение — удобно для «бесконечного» управления.

### Выход из игры (только Sprinter)

Как мы говорили в главе 3, игра — это бесконечный цикл, и «выхода» в обычном смысле нет. Но
под **Sprinter** игра работает под операционной системой DSS, и в неё можно вернуть
управление — функцией `quit_to_dss()` (программа на этом завершается и не возвращается):

```c
#ifdef __SPRINTER__
void quit_to_dss(void);   // объявлена в evo.h, доступна только под Sprinter
#endif
```

Эта функция существует только в Sprinter-сборке, поэтому её вызов оборачивают проверкой
`#ifdef __SPRINTER__` — тогда тот же исходник без изменений собирается и под Evo/ATM (где
выхода нет):

```c
static u8 keys[40];
keyboard(keys);
#ifdef __SPRINTER__
if (keys[KEY_SPACE] & KEY_PRESS) quit_to_dss();   // например, выход по пробелу
#endif
```

На Sprinter клавиша **Esc** приходит в систему как комбинация `Caps Shift + Space`.
Типовой приём: Esc в игре возвращает в меню, а Esc в меню вызывает `quit_to_dss()`. Макрос
`__SPRINTER__` определяется при сборке под Sprinter автоматически.

## Глава 13. Собираем всё вместе: разбор готовой игры

Разберём целиком небольшую программу — поле с прыгающими мячиками. Она показывает фон,
включает спрайты, настраивает палитру, делает плавное проявление и крутит игровой цикл.

**`compile.bat`:**

```bat
set output=sprites.scl
set title=" SPRITES DEMO"
set palette.0=back.bmp        rem палитра фона   -> PAL_BACK
set palette.1=balls.bmp       rem палитра мячей  -> PAL_BALLS
set image.0=back.bmp          rem фон            -> IMG_BACK
set sprite.0=balls.bmp        rem лист спрайтов  -> SPR_BALLS (мячи)
```

**`main.c`:**

```c
#include <evo.h>
#include "resources.h"

// состояние одного мячика: позиция и скорость
struct spriteStruct {
    i16 x, y;     // координаты
    i16 dx, dy;   // скорость по осям
};

#define SPRITES_ALL 22                      // столько мячей на экране
struct spriteStruct spriteList[SPRITES_ALL];

void main(void)
{
    static u8 i;
    static u8 palette[16];

    pal_bright(BRIGHT_MIN);                 // погасить экран, пока готовимся

    // случайные стартовые позиции и направления
    for (i = 0; i < SPRITES_ALL; ++i) {
        spriteList[i].x  = 1 + rand16() % (160 - 8 - 2);
        spriteList[i].y  = 1 + rand16() % (200 - 16 - 2);
        spriteList[i].dx = rand16() & 1 ? -1 : 1;
        spriteList[i].dy = rand16() & 1 ? -1 : 1;
    }

    draw_image(0, 0, IMG_BACK);             // фон в теневой экран
    swap_screen();                          // показать фон
    sprites_start();                        // включить спрайты поверх фона

    // собрать общую палитру: 0..5 — от фона, 6..15 — от мячей
    pal_copy(PAL_BACK, palette);
    for (i = 0; i < 6;  ++i) pal_col(i, palette[i]);
    pal_copy(PAL_BALLS, palette);
    for (i = 6; i < 16; ++i) pal_col(i, palette[i]);

    pal_bright(BRIGHT_MID);                 // проявить (нормальная яркость)

    while (1)                               // игровой цикл
    {
        for (i = 0; i < SPRITES_ALL; ++i) {
            // поставить i-й мяч; картинка i&3 — одна из первых 4 ячеек листа
            set_sprite(i, spriteList[i].x, spriteList[i].y, i & 3);

            // отскок от краёв
            if (spriteList[i].x == 160 - 8  || spriteList[i].x == 0) spriteList[i].dx = -spriteList[i].dx;
            if (spriteList[i].y == 200 - 16 || spriteList[i].y == 0) spriteList[i].dy = -spriteList[i].dy;

            // движение
            spriteList[i].x += spriteList[i].dx;
            spriteList[i].y += spriteList[i].dy;
        }
        swap_screen();                      // показать кадр, вывести спрайты, ждать кадр
    }
}
```

Что здесь происходит, по шагам:

1. **Гасим экран** (`pal_bright(BRIGHT_MIN)`) — чтобы подготовка не мелькала.
2. **Инициализируем** массив мячей случайными позициями и скоростями.
3. **Рисуем фон и показываем его**, затем **включаем спрайты** — теперь они будут рисоваться
   поверх фона на каждом `swap_screen()`.
4. **Собираем палитру** из двух: цвета фона кладём в ячейки 0..5, цвета мячей — в 6..15.
5. **Проявляем экран** (`pal_bright(BRIGHT_MID)`).
6. **Игровой цикл:** двигаем каждый мяч, отражаем от краёв, обновляем позицию спрайта,
   и `swap_screen()` показывает кадр. Спрайты выводятся автоматически.

Обратите внимание на диапазоны (`160-8`, `200-16`) — это границы с учётом «полупиксельной»
координаты `x` (0..152, ширина мяча 8 в этих единицах) и высоты спрайта 16 пикселей.

# Часть IV. Тонкости

## Глава 14. Особенности языка C в этом SDK

Это компактная среда, и C здесь не совсем «настольный». Запомните три правила:

1. **Нет стандартной библиотеки.** Нет `printf`, `malloc`, `string.h` и т. п. Из утилит
   доступны только три функции SDK:
   ```c
   void memset(void* m, u8 b, u16 len);   // заполнить память
   void memcpy(void* d, void* s, u16 len);// скопировать (без перекрытия)
   u16  rand16(void);                     // случайное 16-битное число
   ```
2. **Вся память — статическая.** Динамической памяти нет. Все массивы и буферы объявляйте
   глобально или с `static`.
3. **Крупные локальные массивы объявляйте `static`.** Большой массив внутри функции без
   `static` может тихо сломать программу в рантайме (ограничение стека компилятора). Это
   важнейшее практическое правило — если игра загадочно падает, ищите большой нестатический
   локальный массив:
   ```c
   void foo(void) {
       static u8 buffer[256];   // ПРАВИЛЬНО
       // u8 buffer[256];       // ОПАСНО: может сломаться
   }
   ```

Из мелочей: типы фиксированной ширины (`u8`, `i8`, `u16`, `i16`, `u32`, `i32`) определены в
`evo.h` — пользуйтесь ими, это нагляднее и предсказуемее.

## Глава 15. Система координат и разрешение экрана

- **Разрешение игрового поля — 320×200 пикселей.**
- **Тайлы и изображения:** координаты в знакоместах 8×8 (сетка 40×25). Размеры картинок
  кратны 8.
- **Спрайты:** `x` — с шагом 2 пикселя (значение 0..152), `y` — попиксельно (0..184).
- **Мышь:** `mouse_pos` даёт `x` в том же «половинном» разрешении, что и спрайты; а
  `mouse_delta` — в полном.

Эта модель одинакова на Evo и Sprinter, поэтому игра выглядит и управляется идентично на
обеих машинах.

> **Нативный режим Sprinter (`NATIVE=1`, глава 16).** Только для новых Sprinter-проектов
> модель расширяется: поле **320×256** (сетка тайлов 40×32), спрайтовый `x` — **попиксельно**
> 0..319 (`y` до 240). Это сознательно отличается от EvoSDK, поэтому порты EvoSDK остаются на
> дефолте `NATIVE=0` (320×200, 2px). Пример нативного проекта — `example_native/`.

## Глава 16. Сборка под Sprinter в деталях

### Команды

Из папки проекта:

| Команда | Что делает |
|---------|-----------|
| `make` | собрать игру (EXE для Sprinter) |
| `make exe` | то же, явно |
| `make resources` | только сгенерировать `resources.h` |
| `make assets` | только собрать банк ресурсов |
| `make clean` | удалить промежуточные файлы (`_build/`) |

Имя выходного файла берётся из `set output=` в `compile.bat` (берётся базовое имя, к нему
добавляется `.exe`).

### Компилятор

Сборка под Sprinter использует **SDCC версии 2.9.0** (специально эту версию). Если у вас в
системе стоит другой SDCC, укажите путь к 2.9.0 — либо переменной при запуске, либо в файле
`sprintersdk/config.local.mk`:

```make
SDCC290_BIN_DIR = /путь/к/sdcc-2.9.0/bin
```

> Частая ловушка: команда `sdcc` в `PATH` может быть новой версии (4.5.0). Для текущей
> сборки нужна именно 2.9.0 — поэтому путь задаётся отдельно и не зависит от `PATH`.

### Опции сборки

Передаются как `make ПЕРЕМЕННАЯ=значение`:

- **`PACK_ASSETS=0`** (по умолчанию) — ресурсы пишутся «как есть». Никаких дополнительных
  инструментов не требуется.
- **`PACK_ASSETS=1`** — код и ресурсы **сжимаются** (экономия места на диске). Для этого
  используется упаковщик, входящий в SDK.
- **`UNROLL=0`** (по умолчанию) — компактные циклы вывода графики (меньше код SDK).
- **`UNROLL=1`** — **развёрнутые** (unrolled) циклы вывода спрайтов и синхронизации тайлов:
  быстрее за счёт чуть большего объёма кода SDK. Это компромисс «скорость ↔ объём» —
  включайте, если игре важна скорость рендера, а места хватает. Поведение игры не меняется,
  только производительность.

```sh
make UNROLL=1        # собрать «быстрый» вариант
make                 # вернуться к компактному (UNROLL=0)
```

- **`PAL256=0`** (по умолчанию) — спрайты 16-цветные: цвета 0..15, прозрачным считается
  любой индекс ≥16.
- **`PAL256=1`** — спрайты 256-цветные (Sprinter-расширение): цвета 0..254, прозрачным
  считается только индекс **255**. Нужно для игр, использующих полную палитру Sprinter
  (256-цветные палитры применяются SDK автоматически, без флага). Существующие 16-цветные
  игры собирайте с `PAL256=0` (иначе их прозрачность спрайтов сломается).

- **`NATIVE=0`** (по умолчанию) — **режим совместимости с EvoSDK**: рабочее поле
  **320×200** (отцентрировано в кадре), спрайтовый X — с шагом **2 пикселя** (координата
  0..152). Существующие игры/примеры работают как на Evo.
- **`NATIVE=1`** — **нативный режим Sprinter**: весь экран **320×256** доступен под
  рисование, спрайтовый X — **попиксельный по всей ширине** (0..319). Это для **новых**
  проектов, написанных под Sprinter (см. `example_native/`). Семантика координат отличается
  от EvoSDK, поэтому исходные EvoSDK-игры собирайте только с `NATIVE=0`.

```sh
make NATIVE=1        # новый проект под полный экран и попиксельные спрайты
make                 # режим совместимости (NATIVE=0) -- для портов EvoSDK
```

> В нативном режиме `set_sprite(id, x, y, spr)` принимает `x` как **пиксель** (0..319), а
> `y` — до 240 (экран 320×256). В режиме совместимости `x` — это 2-пиксельные единицы
> (0..152), `y` до 184, как в EvoSDK. На Sprinter параметр `x` 16-битный, поэтому одни и те
> же вызовы компилируются в обоих режимах. Проект задаёт режим в своём `Makefile`
> (`NATIVE := 1`) — как `example_native`.

### Кодировка исходников

Z80-компилятор ожидает однобайтовую кодировку текста. На диске вы можете держать `main.c` в
UTF-8 — при сборке исходники автоматически приводятся к нужной кодировке (CP866) во
временную папку `_build/`. Вам ничего делать не нужно; просто знайте, что комментарии на
русском в исходнике — это нормально.

### Что внутри готового файла

Собранный `.exe` — это **самодостаточная программа DSS**: внутри и код игры, и все ресурсы.
Когда DSS запускает файл, встроенный загрузчик распаковывает код и ресурсы по памяти и
передаёт управление вашей программе. Вам как автору игры об этом думать не нужно — это
делается автоматически.

### Лимиты, о которых стоит помнить

- **Код+данные на C** должны уместиться примерно в **55 КБ**. Если не помещаются — сборка
  честно об этом скажет (а не соберёт битый файл).
- **Ресурсов** может быть очень много (до 3.2 МБ) — при запуске игры они целиком
  загружаются в оперативную память, поэтому их объём ограничен размером ОЗУ, а не диском.

### Две машины из одного исходника

Этот же `main.c` и `compile.bat` собираются и под **ZX Evolution / ATM** (через каталог
`evosdk/`), и под **Sprinter** (через каталог `sprintersdk/`, как описано выше). Менять код
игры не нужно — оба таргета используют одинаковый набор функций `evo.h` с одинаковым
поведением.

## Приложение B. Справочник констант

**Цвет:** `RGB222(r,g,b)` — цвет из каналов 0..3. Яркость: `BRIGHT_MIN=0`, `BRIGHT_MID=3`,
`BRIGHT_MAX=6`.

**Спрайты:** `SPRITE_END = 0xff00` — маркер конца списка.

**Джойстик** (флаги `joystick()`): `JOY_RIGHT`, `JOY_LEFT`, `JOY_DOWN`, `JOY_UP`,
`JOY_FIRE`.

**Мышь** (флаги кнопок): `MOUSE_LBTN`, `MOUSE_RBTN`, `MOUSE_MBTN`.

**Клавиши-состояния** (биты в массиве `keyboard`): `KEY_DOWN` (удерживается),
`KEY_PRESS` (нажата с прошлого опроса).

**Коды клавиш** (индексы в массиве): буквы `KEY_A`…`KEY_Z`, цифры `KEY_0`…`KEY_9`, а также
`KEY_SPACE`, `KEY_ENTER`, `KEY_SYMBOL` (Symbol Shift), `KEY_CAPS` (Caps Shift).

**Логические:** `TRUE = 1`, `FALSE = 0`.

## Приложение C. Карта памяти и формат выходного файла

Для большинства игр это знать не обязательно — приведено для любознательных.

- **Игровое поле** — VRAM на 320×200, два экрана для двойной буферизации.
- **Код и данные C** — единый блок размером до 56320 байт (≈55 КБ).
- **Ресурсы** — разложены по страницам (по 16 КБ), до 200 страниц (3.2 МБ). При запуске
  загрузчик считывает их с диска **целиком в оперативную память**; во время игры SDK
  обращается к нужной странице прямо в памяти (переключая окно адресации), без чтения с диска.
- **Выходной файл** — программа в формате DSS со встроенным загрузчиком: внутри лежат код
  (несколькими блоками) и все страницы ресурсов; при запуске загрузчик раскладывает их по
  памяти и стартует игру.

Технические детали (адреса, страницы, видеорежим, акселератор, звуковые порты) описаны со
ссылками на первоисточники в файле `sprintersdk/HW_NOTES.md`.

## Приложение D. Шпаргалка

**Минимальная игра:**

```c
#include <evo.h>
#include "resources.h"

void main(void)
{
    pal_bright(BRIGHT_MIN);     // погасить
    draw_image(0, 0, IMG_BACK); // фон
    swap_screen();              // показать
    draw_image(0, 0, IMG_BACK); // во второй буфер
    swap_screen();
    pal_select(PAL_BACK);       // палитра
    pal_bright(BRIGHT_MID);     // проявить

    while (1)
    {
        // ... логика и рисование ...
        swap_screen();
    }
}
```

**`compile.bat`:**

```bat
set output=mygame.scl
set title=" MY GAME"
set palette.0=back.bmp
set image.0=back.bmp
set sprite.0=hero.bmp
set music.0=tune.pt3
set soundfx=fx.afb
set sample.0=voice.wav
```

**Памятка по форматам ресурсов:**

| Тип | Формат | Требования |
|-----|--------|-----------|
| `palette` | BMP 16/256 цв. | палитра берётся из файла |
| `image` | BMP 16/256 цв. | размеры кратны 8 |
| `sprite` | BMP **256 цв. (8bpp)** | размеры кратны 16; цвета 0..15 видимы, ≥16 прозрачны |
| `music` | PT3 | — |
| `soundfx` | AFX (`.afb`) | банк из многих эффектов |
| `sample` | WAV | моно, без сжатия |

**Три золотых правила C:** нет stdlib (только `memset`/`memcpy`/`rand16`); вся память
статическая; крупные локальные массивы — `static`.
