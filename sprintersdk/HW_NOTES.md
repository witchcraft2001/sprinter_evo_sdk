# HW_NOTES.md — аппаратная разведка Sprinter (Этап 0)

Свод **проверенных** фактов о железе Sprinter/DSS для порта EvoSDK. Принцип
(`../CLAUDE.md` §2.7): каждый факт — со ссылкой на первоисточник; догадки и
непроверенное помечены явно. Перед использованием любого «магического» порта в коде —
сверять с этим файлом и комментировать ссылкой.

Легенда достоверности: **[V]** — проверено по первоисточнику (equate/заголовок/рабочий
код); **[M]** — из манула (обзор, не сверено с FPGA/кодом); **[?]** — требует проверки
на эмуляторе/железе.

Сокращения источников:
- `ports.h` = `sdcc-sprinter-sdk/include/sprinter/ports.h`
- `video.h`/`bios.h` = `sdcc-sprinter-sdk/include/sprinter/{video,bios}.h`
- `manual/...` = `sprinter_ai_doc/manual/...`
- `modplay/...` = `sources/modplay/src/...` (валидированный рабочий код CBL/звука)
- `EXE_Header.z80` = `Estex-DSS/Shared_Includes/constants/EXE_Header.z80`

## 1. Память и страничная модель

**[V]** Адресное пространство Z80 (64 КБ) = **4 окна по 16 КБ**, у каждого — свой
регистр-селектор физической страницы (`ports.h:11-14`):

| Окно | Адреса Z80 | Порт-селектор |
|------|------------|---------------|
| WIN0 | `0x0000–0x3FFF` | `#82` (PORT_WIN0) |
| WIN1 | `0x4000–0x7FFF` | `#A2` (PORT_WIN1) |
| WIN2 | `0x8000–0xBFFF` | `#C2` (PORT_WIN2) |
| WIN3 | `0xC000–0xFFFF` | `#E2` (PORT_WIN3) |

**[M]** Физическая RAM — страницы по 16 КБ, физ. адрес = `page*16384 + offset`
(`manual/01_architecture/03_memory_map.md`). Размер ОЗУ — от 4 МБ.
**[V]** Запись страницы в окно: `LD A,page : OUT (#E2),A` (порт WIN3) — см. рабочий код
`manual/05_graphics/06_accelerator.md` (FastClearScreen), `modplay`.

Распределение страниц под приложение в DSS — **динамическое** (через DSS/EMM GetMem),
не фиксированное. Это ключевое отличие от Evo (там номера страниц зашиты). См. §10.

## 2. SRAM-кэш (WIN0) — `manual/02_memory/03_cache.md` [V]

- **128 КБ SRAM** на плате; в адресном пространстве — **только WIN0 (`#0000–#3FFF`)** при
  `CASH_ON=1`. Одновременно доступно **до 64 КБ** (4×16 КБ, страница выбирается
  `ROM_RG[1..0]`).
- **0 wait states при турбо 21 МГц** (DRAM ~1.5–2×, ROM/Flash +4 CLK42 ≈ 95 нс/доступ).
  Это и есть причина «горячие циклы — в SRAM».
- Включение/выключение (из `SP2_ACEX.TDF`, защёлкивается бит A7 адреса порта):
  - `IN A,(#FB)` → `CASH_ON=1` (SRAM в WIN0)
  - `IN A,(#7B)` → `CASH_ON=0` (DRAM/ROM в WIN0)
- **ОГРАНИЧЕНИЯ (критично):**
  1. **При `CASH_ON=1` нельзя вызывать `RST #08` (BIOS), `RST #10` (DSS), `RST #30`
     (Mouse)** — их векторы в WIN0 указывают в SRAM. Выключать кэш перед системными RST.
  2. WIN0 при кэше «не видит» DRAM — нужные данные копировать заранее.
  3. IM1-вектор `#38`, таблица IM2 и трамплины в нижних 16 КБ тоже подменяются — либо
     `DI` на время работы с кэшем, либо полностью автономный обработчик в SRAM.
- **[V][?]** Нюанс: `modplay/include/ports.inc:18-27` отмечает, что рабочий код
  `gifview` и `TIMER.EXE` входит в кэш-окно через системную карту
  (`SYS_PORT_OFF=#3C`, `ISA_SYSTEM_PORT=#1FFD`, `SYS_MAP_CACHE=#04`), **а не одним
  `#FB`**. Перед реализацией hot-loop в SRAM — свериться с этим рабочим кодом.

**Применение для порта:** библиотеки `lib_tiles`/`lib_sprites` (горячие циклы вывода) —
кандидаты на размещение в SRAM (WIN0); подготовка пикселей в SRAM → копирование в VRAM
через акселератор (см. §4) быстрее, чем DRAM→VRAM.

## 3. Видео: режимы, палитра, PORT_Y, двойная буферизация

### Режимы
- **[V]** Прямой порт `#C3` (PORT_GFXMODE, `ports.h:17`): `00`=ZX, `01`=320×256×8bpp,
  `10`=640×256×4bpp.
- **[V]** Через DSS SETVMOD (`#50`): `A`=mode, `B`=page (`video.h:12-20`):
  `VMODE_320=0x81` (320×256, 256 цв.), `VMODE_320_16=0x80` (16 цв.),
  `VMODE_640=0x82`. Бит 7: 1=графика.
- **[V]** Размеры: 320×256 (8bpp ⇒ 1 байт/пиксель ⇒ 80 КБ экран) / 640×256 (4bpp).

### Палитра — `manual/05_graphics/05_palette.md`, `video.h`, `bios.h` [V]
- **6-битный RGB** на канал (0–63).
- **ПРЯМАЯ запись (без BIOS, предпочтительно)** — протокол подтверждён MAME
  (`sprinter.cpp`) и на железе (`sdcc-sprinter-sdk/examples/30_paltest`,
  `lib/src/video/fade_apply.s`):
  ```
  OUT (#E2),#50        ; WIN3 = VRAM #50 (сохранить прежнюю страницу)
  OUT (#89),i          ; PORT_Y выбирает ИНДЕКС палитры i (0..255)
  LD (#C3E0),r6<<2     ; R (6-битное значение в старших 6 битах)
  LD (#C3E1),g6<<2     ; G
  LD (#C3E2),b6<<2     ; B
  OUT (#89),#C0 ; safe   OUT (#E2),saved ; restore WIN3
  ```
  VRAM `#50` = 256 строк × 1024 Б; PORT_Y = индекс, смещения `#C3E0/E1/E2` в строке
  декодируются как `palette[PORT_Y]` R/G/B. **DI не нужен** (WIN0 не трогаем); PORT_Y —
  только запись (`IN #89` = состояние CBL). 256 цветов одним циклом, без прерываний.
  **В порте используем этот путь для `pal_*`/фейдов** (Scheme C: код из WIN0, WIN3
  временно = `#50` с save/restore).
- BIOS SETPAL `#A4` (`HL`=index, `D`=R, `E`=G, `A`=B, `bios.h:26`) и
  `video_setpal256_fast.c` — «correct, simple, **slow**» (512 вызовов A4, ~20–30 мс);
  только для разовой загрузки на старте, НЕ для рендера/фейдов.
- **[V] PORT_Y и «мусор»:** после записи в VRAM/работы акселератора PORT_Y `#89` нужно
  вернуть в **`#C0`** (невидимая зона), иначе обращения к VRAM оставляют видимые
  артефакты (`manual/05_graphics/06_accelerator.md:182-190`, `video.h:107-110`).

### Двойная буферизация — `ports.h:18`, `manual/05_graphics/07_double_buffer.md`
- **[V]** Порт `#C9` (PORT_RGMOD): бит 0 — выбор отображаемого буфера, бит 1 — гашение
  экрана (опц.).

## 4. Акселератор (blitter) — `manual/05_graphics/06_accelerator.md` [V]

Перехватывает `LD r,r` на M1-цикле (в обычном Z80 — NOP). Работает на **42 МГц
независимо от турбо**. **Только в нативных режимах** (не в ZX). До **~20× быстрее `LDIR`**
для блоков с VRAM (256 байт: ~37 мкс vs ~780 мкс).

Команды (опкоды из `ACCELER.TDF`):

| Инстр. | Опкод | Действие |
|--------|-------|----------|
| `LD B,B` | `#40` | **Выключить** акселератор |
| `LD C,C` | `#49` | Заполнить блок константой (A) |
| `LD D,D` | `#52` | **Установить размер блока** (далее `LD A,size`, 1–255) |
| `LD E,E` | `#5B` | Вертикальное заполнение |
| `LD L,L` | `#6D` | Копировать строку (HL→DE) |
| `LD A,A` | `#7F` | Вертикальное копирование (шаг 320 байт) |

- **Размер блока — 8 бит ⇒ максимум 256 байт за операцию.** Больше — циклом.
- Функции маскирования **FN_ACC**: `0`=copy, `1`=OR, `2`=XOR, `3`=AND (для спрайтов с
  прозрачностью). Выбор — спец. опкодами `10XXXXXX` (напр. `LD D,(HL)`=`#56`). **[?]**
  точную последовательность выбора функции проверить по `ACCELER.TDF`/рабочему коду.
- **DI обязателен** на время операции; по завершении — `LD B,B` (выкл.) и PORT_Y←`#C0`.
- Шаблон: `di · ld d,d · ld a,size · ld hl,src · ld de,dst · ld l,l · ei · ld b,b`.

**Связь с EvoSDK:** оригинальный `_fast_ldir` («эффективен при bc>12»,
`evosdk/lib_startup.asm:453`) — это софтверный ускоренный LDIR; на Sprinter его роль для
крупных блоков (>12 байт) берёт акселератор. Порог «>12 байт» — ориентир выгодности.

## 5. VRAM-страницы и теневая VRAM — `video.h:23-34`, `manual/05_graphics/01_video_overview.md`

**[V]** Номер VRAM-страницы = `0x5X`, где `X = %TSPP`:
- **T** (бит 3, маска `0x08`, `VRAM_TRANSPARENT`) — пропускать байты `0xFF` при записи
  (аппаратная прозрачность).
- **S** (бит 2, маска `0x04`, `VRAM_ONLY`) — писать только в видео-RAM, не трогая
  DRAM-зеркало.
- **PP** (биты 1–0) — выбор буфера.

Производные режимы записи (диапазоны страниц):

| Страницы | T | S | Поведение | Достоверность |
|----------|---|---|-----------|---------------|
| `#50–#53` | 0 | 0 | Запись в VRAM **и** в DRAM-зеркало (норма) | [V] |
| `#54–#57` | 0 | 1 | Только VRAM (DRAM не меняется) | [V] |
| `#58–#5B` | 1 | 0 | **Прозрачная (пропуск `0xFF`) + зеркало в DRAM** | **[V] на железе** |
| `#5C–#5F` | 1 | 1 | Прозрачная + только VRAM (типично для спрайтов) | [V] |

**Теневая VRAM / восстановление фона:** DRAM-зеркало хранит копию видеоданных, что
позволяет быстро восстанавливать фон (копировать чистый фон из DRAM обратно в VRAM).

> **[V] ПОДТВЕРЖДЕНО НА РЕАЛЬНОМ ЖЕЛЕЗЕ (решение архитектора):** совмещённый режим
> **прозрачность + запись в DRAM-зеркало** (`#58–#5B`) **РАБОТАЕТ** на реальном
> компьютере; прежнее «не работает» было **багом MAME**. Ограничение `../CLAUDE.md` §7.1
> **снято** — в порте используем аппаратный путь, без софтверного фолбэка.
> ⚠️ **MAME может всё ещё некорректно показывать этот режим** → проверять на реальном
> железе / исправленном MAME, не доверять MAME для `#58–#5B`.

## 6. Звук

### 6.1 CBL (Covox Blaster) — `modplay/lib/cbl.asm`, `modplay/include/ports.inc` [V, валидировано]
**Разрешение конфликта сводок** (`#88/#89` vs `#4E/#4F`): это **разные** механизмы.
CBL — это FIFO/DMA-контроллер Covox, для буферизованного воспроизведения PCM:
- **`CBL_CTRL = #004E`** — управление (16-битный порт, `OUT (C),A` при `BC=#004E`).
- **`CBL_DATA = #004F`** — данные FIFO (16-битный порт, `OUT (C),A` при `BC=#004F`).
- **FIFO 256 байт**; долив по **128 байт** на каждый half-boundary.
- **Синхронизация — поллинг бита 7 порта `#FE`** (`CBL_INT_FE`): в CBL-режиме
  `#FE.bit7 = (CBL_CNT ^ CBL_WA) & #80`. Управляющий байт с **bit4=1** включает
  переключение `#FE.bit7`. (Это и есть «вектор/буфер CBL» из правок архитектора —
  НЕ CTC.)
- Управляющие байты «вкл.» (rate): **`#D9 / #DA / #DB`** для **11 / 15 / 21 кГц**
  (`cbl.asm:48-50`, `MS_CBL_CTRL_RUN`). «Выкл.» = запись `0` в `#004E`.
- **НЕЛЬЗЯ `OTIR`** для долива FIFO: OTIR декрементирует B → меняет старший байт порта в
  DCP-декодере. Только `OUT (C),A` при `B=0` (`cbl.asm:238-255`).
- Порядок init (Path A, `cbl.asm:25-53`): `DI` → CBL off (`#004E`←0) → flush FIFO
  256×`0x80` → пре-рендер буфера → CBL on (`#004E`←rate-byte). На время Path A — `DI`.
- Shutdown (`cbl.asm:261-278`): `DI` → `IM 1` → CBL off → flush 256×`0x80` → `EI`.

**Связь с EvoSDK `sample_play`:** семантика оригинала — блокирующее воспроизведение с
запретом прерываний; ложится на Path A (DI, поллинг `#FE.bit7`).

### 6.2 Простой Covox-DAC (отдельно от CBL) — `ports.h:35-36` [V]
- `#88` (PORT_COVOX) — 8-битные данные DAC; `#89` (PORT_COVOX_MODE) — режим.
  Это «сырой» Covox без FIFO; не путать с CBL (§6.1).

### 6.3 AY-3-8910 — `ports.h:32-34` [V]
- `#8C` адрес регистра, `#8D` запись, `#8E` чтение. Для PT3 и AFX.

### 6.4 vsync через CBL/`#FFFE` бит 5 — `video.h:65` [V]
- `video_vsync` ждёт начало кадра по биту 5 порта `#FFFE` (16-битный FE) при доступном
  CBL. Учесть при реализации `vsync`/`swap_screen`.

## 8. Ввод — `ports.h:38-41` [V]

**[РЕШЕНО] Фаза 1 — ввод = калька EvoSDK** (`evosdk/lib_input.asm`), с поправкой портов
под Sprinter:
- **Клавиатура ZX-матрица:** порт `#FE`, 8 рядов (маска строки в B), биты 0–4 = клавиши
  (0=нажата). `_keyboard` заполняет 40-байтный массив; коды `KEY_*` = смещения в нём.
  **Переносится дословно** — Sprinter поддерживает ZX-матрицу `#FE` (manual; `modplay`
  читает `#FE` row `#7F`). Бит 7 `#FE` занят CBL-флагом — клавиатуре не мешает (биты 0–4).
- **Kempston-джойстик:** `in a,(#1F)`, биты 0–4 (right/left/down/up/fire). Логика как в
  EvoSDK `_joystick` (курсор через `#FE` + Kempston), но **без Evo-DOS/shadow-обёртки**
  вокруг чтения `#1F` (`#3ff7/#ff77/#3d2f`) — на Sprinter простое `in`.
- **Мышь Kempston:** clip/delta-логика (`poll_mouse`, `mouse_apply_clip`, понижение
  X-разрешения) — **дословно**. НО адреса портов другие: EvoSDK `#FBDF`(x)/`#FFDF`(y)/
  `#FADF`(кнопки) → **Sprinter `#58`-семейство** (`ports.h`: btn `#58`, X `#158`, Y `#358`).
  **[?]** Точную адресацию Kempston-мыши Sprinter сверить на эмуляторе/железе (есть и BIOS
  Mouse API `RST #30` / DSS API — на потом).
- **PS/2 SIO:** данные `#18`, статус/команда `#19` (`ports.h:50-51`).

## 9. Формат EXE (DSS) — **СВЕРЕНО по коду `Estex-DSS/DSS/API/Execute.ASM`** [V]

Заголовок (512 байт) **перед** телом программы. Поля (смещения), подтверждены тремя
способами в EXEC (#40): закомментированной структурой `EXEBUFF` (Execute.ASM:772-790),
обращениями кода (`EXEBUFF.LD_ADDR`/`PC_REG`/`SP_REG`/`VERSION`) и комментариями рутины
(Execute.ASM:61-65):

| Смещение | Поле (имя в DSS) | Значение |
|----------|------------------|----------|
| 0–2 | сигнатура | `'EXE'` (EXEC проверяет первые 2 байта = `"EX"`) |
| 3 | `VERSION` | версия; EXEC отвергает версии **новее** поддерживаемой (`MINIMUM_EXE_VERSION`). Текущая = **1** |
| 4–5 | `OFFCOD1` | смещение кода в файле, мл. слово (= 512) |
| 6–7 | `OFFCOD2` | смещение кода в файле, ст. слово (= 0) → файловый офсет тела = 512 |
| 8–9 | `LOADER` | размер первичного загрузчика; **0 = нет** (иначе PRELOAD-механизм) |
| 10–15 | reserved | `#0000` |
| 16–17 | **`LD_ADDR`** | **адрес загрузки в память**, диапазон **`#4100–#FFFF`** |
| 18–19 | **`PC_REG`** | точка входа (DSS делает `JP` сюда) |
| 20–21 | **`SP_REG`** | адрес стека (DSS делает `LD SP,(SP_REG)`) |
| 22–511 | — | резерв / инфо-текст |

**Подтверждено:** `dss_exe.py` пишет ровно эту раскладку (load@16, entry@18, stack@20,
ver@3, офсет кода@4) → **формат корректен и совместим с DSS.** Версия 1 принимается.

**⚠️ Мануал `04_dss/05_dss_exe.md` «Вариант 2» (load@`0x0A`, `#8100`) — НЕВЕРЕН для Estex-DSS**
(EXEC читает load@16, не @0x0A). Использовать раскладку из этой таблицы. «Вариант 1» манула
(entry@16/18, stack@20) — совпадает с реальным DSS.

**Загрузка тела:** EXEC читает код из файла (с офсета `OFFCOD`) в память по `LD_ADDR`,
маппя страницы в WIN1/2/3 по окну `LD_ADDR` (`AND #C0`). То есть **DSS грузит всё тело
после заголовка в адресное пространство по `LD_ADDR`.**

### 9.1 Монолитный EXE с первичным загрузчиком (СТАНДАРТ, цель Этапа 2) [V — `kode/KodeEXE.asm`]

«Ассеты+код внутри одного EXE» — стандартный, широко используемый паттерн Sprinter
(Kode, fn и др.). Механизм (PRELOAD), сверен по `Execute.ASM` + рабочему `kode/KodeEXE.asm`:

- **Заголовок:** `LOADER`@8 = **размер первичного загрузчика** (≠0 → режим PRELOAD);
  `LD_ADDR`@16 и `PC_REG`@18 = старт загрузчика; офсет кода@4 = 512.
- **DSS в PRELOAD** грузит из файла только `LOADER` байт (сам загрузчик) по `LD_ADDR`,
  прыгает на `PC_REG`, и **оставляет файл ОТКРЫТЫМ**.
- **Загрузчик получает file handle из `PSP[IX-3]`** (DSS кладёт его туда в `M_PSP`;
  PSP: `IX-3`=FM, `IX-2`=mem id, `IX-1`=уровень задачи, `IX+0`=длина cmdline, `IX+1..`=cmdline).
- Загрузчик: `BIOS.GetMem`/`GetMemBlkPages` (выделить страницы) → последовательно
  `Dss.Read` блоки тела из открытого файла → **`DePACK` (HRUST `.hst`)** в нужные страницы
  → `Dss.Close` → выставить пейджинг + IM2 + SP → прыгнуть в код программы.
- **Тело EXE** = [512 hdr][код загрузчика][блобы тела], где блобы — HRUST `.hst`
  (`INCBIN`). **Это ровно формат `pack_spk.py --mhmt -hst`**, распаковываемый `DePACK`.

➜ **План Этапа 2 для порта:** `loader.asm` (наш первичный загрузчик) + расширить
`dss_exe.py` до монолита: header с `LOADER`@8=размер loader, далее loader, далее блобы
(SDK→SRAM/WIN0, C-код→`#2400+`, ассеты→страницы). Загрузчик ставит карту Scheme C, `I`
(IM2), `SP`, прыгает в рантайм. Текущий `dss_exe --assets` (слепой append, `LOADER`=0) —
временный стаб; в Этапе 2 заменяется на монолит с PRELOAD-загрузчиком.

Выход из программы — DSS #41 (`LEAVE`): `RST #10`, `B`=код возврата (Execute.ASM:529+).

## 10. Карта памяти: EvoSDK (факт) → Sprinter (ПРИНЯТАЯ раскладка)

**Решение архитектора:** SDK собирается с `#0000`, **целиком живёт в SRAM (WIN0)**; за ним
1 КБ стека; затем — код+данные C. Бюджет C сохраняется 1:1 с EvoSDK (те же ~55 КБ): 9 КБ
(8 КБ SDK + 1 КБ стек) резервируются как и в Evo, только **снизу**, а не сверху. Это даёт
SDK постоянный SRAM (горячие циклы на 0-wait 21 МГц) **без подмен окон**.

### 10.1 EvoSDK — фактическая карта (источники: `evosdk/lib_startup.asm`, `crt0.s`, `tools_src/evoresc/evoresc.cpp`) [V]

Evo/ATM — 4 слота по 16 КБ (порты `#37f7/#77f7/#b7f7/#f7f7`). По `evoresc.cpp`
(`STARTUP_ADR=#e000`, `STACK_SIZE=#400`, `cc_page={12,13,14,15}`):

| Z80-адрес | Содержимое |
|-----------|------------|
| `#0000–#DBFF` | **C код+данные** — старт `#0000`, код с `#0006`; до **4 страниц** (12/13/14/15, slots 0–3). Потолок = `STARTUP_ADR − STACK_SIZE = #DC00 = 56320 байт` ≈ **«55 КБ»** (`evoresc.cpp:830`). |
| `#DC00–#DFFF` | **стек** 1 КБ (`STACK_SIZE`), `SP=#DFFF` вниз |
| `#E000–#FFFF` | **SDK** (`startup.bin` 8 КБ): render-код, очереди `#FB00`, `tileUpdateMap #FD00`, IM2 `#FDFD`, векторы `#FE00`, переменные `#FF40+` |

➜ SDK **НЕ отдельная страница** — это верхние 8 КБ, делящие верхнюю страницу с верхом
C-образа и стеком. Вызов из C: обёртки `evo.c` → `jp <абс.адрес>` по `startup.h`
(`_DRAW_TILE=0xE646`, …); верхнее окно всегда замаплено. Подкачиваемые классы страниц
(вне 55 КБ): экраны `1/3/5/7`, sprite-bg `8–11`, sprite-table `6`, sound `0`, palette `4`,
gfx `16`.

### 10.2 Sprinter — ПРИНЯТАЯ раскладка (Scheme C: SDK снизу, в SRAM) [V — решение архитектора]

| Z80-адрес | Окно | Содержимое |
|-----------|------|------------|
| `#0000–#1FFF` (~8 КБ) | **WIN0 (SRAM)** | **SDK целиком** (render-код, IM2, очереди, таблицы) — 0-wait 21 МГц |
| `#2000–#23FF` (1 КБ) | WIN0 (SRAM) | **стек** (`SP=#23FF`, вниз) |
| `#2400–#FFFF` (56320 Б) | WIN0(верх)/WIN1/WIN2/WIN3 | **код+данные C** — тот же бюджет, что EvoSDK |

➜ **Бюджет C = `#2400–#FFFF` = 56320 байт = ровно «55 КБ» EvoSDK.** Граница `#2400`
держится, пока SDK ≤ 8 КБ; если SDK вырастет — база C поднимается, бюджет должен остаться
в коридоре ±2–5 % (`CLAUDE.md` §2.4). Кэш `CASH_ON` включён постоянно (WIN0 = SRAM); низ
C-кода (`#2400–#3FFF`) тоже попадает в SRAM (быстрее). Стек — в owned-странице SDK (WIN0)
→ правило owned-page соблюдено. База C ≠ `#0000`, а ≈ `#2400` (SDCC `--code-loc/--data-loc`);
`startup.h` регенерируется с низкими адресами SDK (`#0000–#1FFF`). На исходники игр НЕ
влияет (SDCC релоцирует; API `evo.h` неизменен).

### 10.3 Что нужно изменить/учесть при этой раскладке

1. **WIN0 нельзя ремапить во время работы SDK** (там исполняется SDK из SRAM). Места, где
   EvoSDK открывал **slot0** для своих целей, перенести на WIN1/WIN2/WIN3 (любое
   подходящее):
   - `pal_get_address` (в `_pal_select`/`_pal_copy`, `lib_startup.asm`): мапит `PAL_PAGE`
     в slot0 для чтения палитры. → мапить в WIN1/2/3: сохранить текущую страницу окна
     (`in a,(#A2/#C2/#E2)`), подменить на `PAL_PAGE`, прочитать, восстановить.
     **`PAL_PAGE`** (Evo: физ. страница 4) — страница данных SDK: по `#0000` —
     предопределённые палитры (16 цветов × 16 байт RGB222 на палитру, индекс = ID;
     читают `pal_select`/`pal_copy`); по `#1000` (`IMGLIST_ADR`) — таблица изображений
     (4 байта/img: смещение тайла lo/hi + ширина + высота; для `select_image`/`draw_*`).
     Источник: `evoresc.cpp`.
   - `setSlot0`/`RestoreMemMap0` — пересмотреть (WIN0 теперь фиксирован за SDK).
2. **Системные `RST #08/#10/#30` + кэш.** Векторы `#0008/#0010/#0030` теперь = SDK-код в
   SRAM. Вызов DSS/BIOS через трамплин **вне WIN0** (в WIN1-3): `DI` → cache off
   (WIN0→system ROM) → `RST` → cache on (WIN0→SRAM) → `EI`. Аналог `DOS_3D13` EvoSDK
   (`manual/02_memory/03_cache.md`: «нельзя RST при CASH_ON»).
3. **IM2.** Обработчик — SDK (WIN0/SRAM); таблица векторов — в WIN0/SRAM (напр. `I=#1F`),
   читается при cache on. На время RST-трамплина (cache off) — `DI`.
4. **Видео/рендер.** [РЕШЕНО] **VRAM-приёмник → WIN3** (`#50–#5F`, строка через PORT_Y
   `#89`; акселератор делает VRAM↔VRAM в пределах одного окна — второе окно не нужно).
   **Источник gfx/спрайтов → WIN1/WIN2.** Рендер сохраняет страницу окна перед подменой и
   восстанавливает (`in a,(#E2)` для WIN3 и т.д.) — как Evo свапал slots 1/2. WIN0 (SDK)
   и стек неизменны → возврат в C безопасен. **Внимание:** IM2 (звук) временно занимает
   WIN1/WIN2 и восстанавливает их — разносить с gfx-источником или тоже save/restore.
5. **Загрузчик** (Sprinter-only, грузится в `#4100`): выделяет DSS-страницы, раскладывает
   SDK-образ в SRAM-страницу (WIN0) и C-образ в свои страницы, ставит `I`/`SP`, прыгает в
   SDK-вход. Не-1:1 адреса — только в нём.

### 10.4 Сохраняем 1:1 (против граблей `evosdk_libs`)
- **Бюджет C код+данные = 56320 байт (`#2400–#FFFF`)** = «55 КБ» EvoSDK — без урезания.
- API `evo.h` неизменен; вход/база C — деталь линкера, на исходники игр не влияет.
- Те же роли классов страниц (экраны, спрайт-буферы, sprite-table, sound, palette, gfx) —
  выделяются через DSS (вместо фикс. номеров Evo).
- Стек 1 КБ (как `STACK_SIZE` Evo), в owned-странице.

### 10.5 Открытые решения архитектора
- ✅ VRAM-приёмник → **WIN3**; gfx-источник → WIN1/WIN2 (п.10.3.4).
- Какое из WIN1/2/3 использовать под временную подмену для `PAL_PAGE` (п.10.3.1) — вероятно
  то же WIN1/WIN2, что и под gfx; уточнить при реализации.
- Кол-во/назначение DSS-страниц под экраны и спрайт-буферы (паритет с Evo).
- Точная граница SDK/стек/C (зависит от итогового размера Sprinter-SDK; цель — держать
  базу C на `#2400`, т.е. SDK ≤ 8 КБ).

## 13. Формат ресурсов (подтверждён по `evosdk_libs`, заимствуем) [V]

Проверено: `evo_sprite_render.s`, `evo_sprite_blit.s`, `evo_sprite_bg.s`,
`evo_draw_tile.s`, `evo_screen.s`, `evo_palette.c`, `tools/evoasm.py`. Формат и работа с
accel — грамотны и в основном оптимальны (это asm-примитивы, не «C-ядро» — заимствуем).

**Видеорежим:** 320×256×**8bpp** (1 байт/пиксель) — даёт 320-ширину под 320×200 EvoSDK,
16 цветов как подмножество 256, попиксельную прозрачность `0xFF` и побайтовый accel.

**Раскладка ассетов (ASSETS.DAT, magic `EVOS`):**
- **Тайл 8×8 = 64 Б** (8 рядов × 8 байт, row-major). Изображение = последовательность
  тайлов. Поиск: `page=high(N)`, `offset=low(N)*64`. **256 тайлов = ровно страница 16 КБ.**
- **Спрайт 16×16 = 256 Б** (16 рядов × 16 байт). Поиск: `bank=(id>>6)&3` →
  `evo_sprite_cache_pages[bank]`, `offset=(id&0x3F)*256`. **64 спрайта = ровно 16 КБ.**
  ➜ Индекс напрямую → (страница, смещение) сдвигами/масками: **O(1), без поиска — оптимум.**
- **Палитра:** `[u16 count][count×3 байта BMP-RGB]`, count 16/256; старшие 6 бит → DAC.

**Accel ↔ размер блока (порог ~13 байт — соблюдён):**
- Спрайт (16 Б/ряд) → accel `LD L,L`; фон-restore (16 Б, same-addr mirror→VRAM) → `LD L,L`;
  `clear`/заливка (160 Б) → `LD C,C`. **Тайл (8 Б/ряд) → развёрнутый `LDI`, НЕ accel**
  (8 < порога; accel был бы медленнее — правильно).
- Вертикальный accel `LD A,A` не используется (не нужен при row-major).

**Прозрачность/фон:** спрайты через VRAM-страницу `0x5C` (прозрачность + VRAM-only) →
`0xFF` отбрасывается HW, DRAM-зеркало чисто → restore = accel same-addr копия зеркало→VRAM.

**Доработать в порте (не блокеры):**
- Палитра: `evosdk_libs` применяет послотно через `bios_setpal` (медленно). **В порте —
  прямой порт-протокол (§3: WIN3=#50, PORT_Y=индекс, `#C3E0/E1/E2`=RGB), без BIOS.**
- `draw_image` может батчить непрерывные ряды в широкие accel-копии (для `draw_tile`
  per-tile-контракт оставляет `LDI`).
- 8bpp удваивает байты тайла/спрайта vs 4bpp EvoSDK → больше страниц ассетов (в бюджет
  кода 55 КБ НЕ входит).

**Аппаратные keyed-тайлы (`draw_tile_key`) через `#58` — готовый приём для переиспользования**
(референс: git-stash `HW-keyed 0x58 experiment` в `evosdk_libs`, ждал именно подтверждения
`#58` на железе — теперь подтверждено, см. §5):
- Манифест: `set color_key.N=K` — картинка N рисуется **только** keyed, индекс `K` —
  прозрачный. `evoasm` ремапит `K → 0xFF` в пикселях этой картинки и ставит per-record
  флаг `hw_keyed` (можно в поле `reserved` EVOS-записи IMG). `K` ∈ 0..254 (255 зарезервирован
  как `0xFF`-сентинел прозрачности — согласуется с правилом спрайтов «индекс ≥16 → 0xFF»).
- Рантайм `draw_tile_key` для hw_keyed-листа: `WIN3=#58` (T=1 прозрачность + S=0 зеркало
  обновляется) + **тот же быстрый развёрнутый `LDI`-burst, что и unmasked** (без per-byte
  CPU-сравнения). HW сам отбрасывает `0xFF`. **~6× быстрее** старого keyed-блита; зеркало
  обновляется → восстановление фона спрайтов поверх keyed-тайлов (текст и т.п.) работает.
- ⚠️ Нельзя объявлять `color_key` для картинки, рисуемой и keyed, и unkeyed (ремап `K→0xFF`
  испортит unkeyed-вывод) — такие остаются на CPU-фолбэке для keyed-вызовов.
- Для порта: применить в Этапе 3 (`draw_tile_key`) + добавить `color_key.N` в `assetpack.py`.

## 14. Формат бандла ассетов `assets.dat` (EVOS) — источник истины [V]

Производит `sprintersdk/tools/assetpack.py`; **загрузчик/рендер SDK (Этап 2/3) обязаны
читать этот формат байт-в-байт.** Все поля little-endian.

**Заголовок (16 байт):**
| Смещение | Тип | Поле |
|----------|-----|------|
| 0 | u32 | magic = `'EVOS'` = `0x534F5645` |
| 4 | u16 | version = 4 |
| 6 | u16 | record_count |
| 8 | u32 | file_size (всего байт) |
| 12 | u32 | reserved = 0 |

**Таблица записей** (сразу за заголовком, по 16 байт на запись):
`u8 type · u8 id · u16 width · u16 height · u16 reserved · u32 offset · u32 length`
(`offset`/`length` — payload в этом же файле). Записи отсортированы по `(type, id)`.

**Коды типов:** `0=PAL · 1=IMG · 2=SPR · 3=MUS · 4=SFX · 5=SAM`.

**Payload по типам:**
- **PAL** — `[u16 count][count×(R,G,B)]`, 8-битные каналы BMP (старшие 6 бит → DAC).
  `count` = 16 (4bpp BMP) или 256 (8bpp).
- **IMG** — тайлы 8×8 по **64 Б** (8 рядов × 8 байт), row-major по листу; `width/height`
  изображения в полях записи. Тайл N внутри картинки: offset `N*64`.
- **SPR** — **по одной записи на ячейку** 16×16, **256 Б**; `0xFF` = прозрачный (исходный
  индекс ≥ 16); `id` = глобальный sprite-id (кумулятивный).
- **MUS** — сырые байты PT3.
- **SFX** — сырой AFX-банк (одна запись, `id=0`; эффекты индексируются внутри банка).
- **SAM** — 8-битный беззнаковый моно-PCM (центр 128); `reserved` = управляющий байт CBL
  (`#D9/#DA/#DB`, см. §6.1).

**Контракт ID (синхронен с `resources.h` от resgen):** PAL/IMG/MUS/SAM — последовательно в
лексикографическом порядке `SET` (как makeresh); SPR — кумулятивный счётчик ячеек.
Пропуск sprite-листа (нет файла / не 8bpp / не кратно 16) — **общая функция
`resgen.bmp_sprite_count`** в обоих инструментах, чтобы SPR-ID не разъезжались.

### 14.1 Опциональная HRUST-упаковка `SPK1` [V]

Источник: `sdcc-sprinter-sdk/tools/pack_asset.py`, `sdcc-sprinter-sdk/docs/*`; локальные
копии инструментов лежат в `sprintersdk/tools/bin/` (`mhmt` для macOS/Linux-сборки,
`hrust.exe` — Windows HRUST-компрессор из `kode/Tools/hrust.exe`; `mhmt.exe` в
`kode`/`flexnavigator` не найден).

По умолчанию `PACK_ASSETS=0`, и `sprintersdk/tools/assetpack.py` пишет raw `EVOS` прямо в
`_build/assets.dat`.

При `PACK_ASSETS=1` make-цепочка такая:
1. `assetpack.py` пишет raw `EVOS` в `_build/assets.raw.dat`;
2. `pack_spk.py` режет raw файл на чанки по 16 КБ, сжимает каждый через
   `mhmt -hst -zxh`, проверяет `mhmt -d`, и пишет `_build/assets.dat` как контейнер
   `SPK1`.

`SPK1` header: `BYTE 'SPK1'`, `BYTE version=1`, `BYTE chunk_count`, `WORD reserved=0`.
Дальше для каждого чанка: `BYTE flag` (`0=raw`, `1=HRUST`), `WORD raw_len`,
`WORD data_len`, затем `data_len` байт payload. Если сжатый чанк не меньше исходного,
пишется raw-чанк (`flag=0`). Сборка без `mhmt` не ломается, пока `PACK_ASSETS=0`.
